## V96 Notes

### Optimizations implemented (all 4 in one batch)

The agent implemented all four optimizations together; individual per-optimization
benchmarks are not available. The combined effect is documented here.

**Opt 1 — Remove redundant TLS writes in ContextScope**
`MemoryManager.hpp`: removed `PythonEnvironment::setCurrentContext(ctx_)` from
`ContextScope` constructor and `setCurrentContext(parent_)` from the destructor.
`s_threadContext` is set once by `registerContext()` at thread startup and never
needs to be updated again; `getPendingException`/`setPendingException` only require
any valid context on the same thread, so the root context is always sufficient.
Saves 2 TLS writes per function invocation.

**Opt 2 — Extend FunctionMetaCache with bytecode/consts/names/nativeBc pointers**
`ExecutionEngine.cpp`: FunctionMetaCache now stores `co_bytecode`, `co_consts_tuple`,
`co_names_tuple`, `nativeBc`, `hasClosure`, `nConsts`, `nNames`. The BUILD_FUNCTION
cache construction uses a variable-length `new char[sizeof(FunctionMetaCache) +
(nConsts+nNames)*sizeof(ptr)]` buffer. In `runUserFunctionCallRaw`, these fields
replace 5 cross-DSO `getAttribute` calls per invocation (co_code, co_consts, co_names,
co_bytecode_native, closure check).

**Opt 3 — Flat C arrays for co_consts and co_names in executeBytecodeRange**
Inline pointer arrays laid out immediately after the FunctionMetaCache struct allow
OP_LOAD_CONST and OP_LOAD_GLOBAL (name string retrieval) to use a direct C array
index instead of `ProtoTuple::getAt()` (AVL tree traversal cross-DSO). The arrays
are passed as `const ProtoObject** nativeConsts, nativeNames` to executeBytecodeRange.

**Opt 4 — Replace hasOwnAttribute with getOwnAttributeDirect in OP_CALL_FUNCTION**
`hasOwnAttribute(codeString)` was used to detect user-defined functions in the
CALL_FUNCTION dispatch. Replaced with `getOwnAttributeDirect(fnMetaCacheString)`,
which returns the cache pointer directly and avoids a second attribute lookup.

### Analysis

The combined improvement on `call_recursion` is ~52ms (−1.8%) for fib(25)/242K calls.
Each optimized attribute removal saves ~0.2µs per call (5 calls × 242K = ~240µs total),
consistent with the measured delta.

The remaining bottleneck is not codeObj attribute reads but the mandatory per-call
overhead of the cross-DSO `ProtoContext` constructor/destructor boundary and the
`executeBytecodeRange` call itself. Reducing this would require either:
1. Inlining the inner loop (requires static linkage or LTO across DSO boundary), or
2. Rewriting the most common bytecode sequences as a native trampoline.

`memory_pressure` geomean variance is from the GC deferral design (intentional);
exclude from ratio comparisons per project convention.
