## V98 Notes

### Fix: Compute actual max stack depth per function; replace hardcoded 4352-slot buffer

**Root cause found**: Every Python function call allocated a heap array of `nLocalVars + 4352`
slots (`= nLocalVars + 256 + PYTHON_STACK_BUFFER(4096)`), bypassing the `ContextScope` SBO
(Small Buffer Optimisation) entirely. The SBO in `MemoryManager.hpp` had a 24-slot inline
buffer — any function with `co_automatic_count > 24` fell back to `new const ProtoObject*[N]`
heap allocation plus a full `std::fill` zero-initialisation of all N slots.

For `fib(n)` with 1 local variable: `co_automatic_count = 4353`.
- `new const ProtoObject*[4353]` → 34,824 bytes per call
- `std::fill(ptr, ptr+4353, PROTO_NONE)` → 34,824 bytes written (544 cache lines)
- `delete[] ptr` on every return

For `fib(25)×5` (≈1.2M recursive calls): 1.2M × (malloc + 34 KB memset + free) ≈ 3 s in
allocator overhead alone, matching the `perf` profile that showed 24.6% cumulative time in
`_int_free` from `ContextScope::~ContextScope()`.

**Fix implemented**:

1. **Stack depth tracking in `Compiler`** (`include/protoPython/Compiler.h`):
   Added `currentStack_` and `maxStack_` fields, updated by `emit()` via a new
   `stackEffect(int op, int arg)` function that maps each opcode to its net stack delta.
   `getMaxStack()` accessor exposes the result to callers.

2. **`stackEffect()` in `Compiler.cpp`** (added before `emit()`):
   Covers all 60+ opcodes: loads (+1), stores (-1), binary ops (-1), builders (1−arg),
   CALL_FUNCTION (−(arg+1) for modern NULL-sentinel layout), comprehension helpers, etc.
   Unknown opcodes default to 0 (conservative: overestimates, never undersizes the array).

3. **Three compiler functions updated** (`compileFunctionDef`, `compileLambda`,
   `compileAsyncFunctionDef` / generator path — all in `src/library/Compiler.cpp`):
   ```cpp
   // OLD:
   automatic_count = static_cast<int>(varnamesOrdered.size()) + 256;
   // NEW (set after body compilation):
   automatic_count = static_cast<int>(varnamesOrdered.size());
   ...
   if (!forceMapped) automatic_count += bodyCompiler.getMaxStack() + 16;
   ```
   16-slot safety buffer covers edge cases not tracked by `stackEffect()` (e.g., exception
   handling temporaries, `SETUP_WITH` frame entries).

4. **`makeCodeObject` in `Compiler.cpp`**:
   Removed `+ PYTHON_STACK_BUFFER` from `co_automatic_count` storage:
   ```cpp
   // OLD: ctx->fromInteger(automatic_count + PYTHON_STACK_BUFFER)   // +4096
   // NEW: ctx->fromInteger(automatic_count)
   ```

5. **`SBO_SLOTS` in `MemoryManager.hpp`**: Increased from 24 to 64.
   With `automatic_count = nLocals + maxStack + 16`, typical functions (fib: 22 slots,
   most stdlib: 20–50 slots) now fit in the inline SBO buffer — zero heap allocation.

### Analysis

**call_recursion** improved 75% (−2039ms) because each `fib()` frame now allocates 22 slots
instead of 4353, fitting in the 64-slot SBO buffer. Zero heap allocation per call: `malloc`,
`memset(34KB)`, and `free` are completely eliminated for ~1.2M recursive calls.

**int_sum_loop, list_append_loop, str_concat_loop, range_iterate** improved 25–57% because
every loop body involves function-scope bytecode dispatch with the same SBO benefit — the
implicit module-scope and function-scope frames no longer heap-allocate oversized slot arrays.

**startup_empty** improved 49% because module load involves many small function compilations
(importlib, bootstrap modules) that now use SBO slots.

**multithread_cpu** improved 43% for the same reason: each thread dispatches function
calls without heap-allocating per-call slot arrays.

**attr_lookup** improved only 6% because `PythonEnvironment::getAttribute` is called on
every attribute read and its overhead is dominated by dictionary traversal, not slot allocation.

### Remaining overhead analysis

`call_recursion` is now 13.55× slower than CPython (down from 47.29×). The remaining gap
is now dominated by:
1. **ProtoContext constructor overhead**: cross-DSO calls to `ProtoContext::ProtoContext()`
   even when `parameterNames == nullptr`, including list size queries and thread-local context
   registration — these cannot be inlined across the shared-library boundary.
2. **ProtoList-based argument passing**: `ctx->newList()` + `appendLast` per call in the
   slow path of `OP_CALL_FUNCTION`, even when the fast path avoids it.
3. **Dynamic attribute lookups**: `getOwnAttributeDirect` for function metadata on every call.

True profiling (`perf record`) after V98 is needed to identify the dominant remaining cost.
