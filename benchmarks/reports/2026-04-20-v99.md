## V99 Notes

### Fix: Replace function-local `static const bool` in `diagEnabled()` with namespace-scope initializer

**Root cause identified via perf profiling of V98**: `get_env_diag()` and
`protoPython::diagEnabled()` together accounted for ~5% of CPU time (1.80% + 1.50% self +
0.95% + 0.70% PLT stubs = 4.95%) despite the value being logically constant for the process
lifetime. The underlying issue is a C++ language rule:

A function-local `static` variable with a non-trivially-constructible initializer:
```cpp
inline bool diagEnabled() {
    static const bool val = (std::getenv("PROTO_ENV_DIAG") != nullptr);
    return val;
}
```
…requires the compiler to emit a guard-check sequence on **every invocation**:
1. Load the guard flag from a thread-local or global atomic location (`__tls_get_addr`)
2. Test whether initialization has completed (branch)
3. If not: call `__cxa_guard_acquire`, run the initializer, call `__cxa_guard_release`
4. Return the cached value

Even after initialization, steps 1 and 2 remain on every call — this is the source of the
`__tls_get_addr` entries (2.67% + 1.86% = 4.53%) seen in the V98 perf profile.

Because `get_env_diag()` is called on every bytecode dispatched (the branch `if
(get_env_diag())` wraps every diagnostic `fprintf` in `executeBytecodeRange`,
`PythonEnvironment.cpp`, `BuiltinsModule.cpp`, etc.), the accumulated cost over millions of
bytecodes is substantial.

**Fix** (`include/protoPython/DiagUtils.h`):

```cpp
// OLD — guard check on every call:
inline bool diagEnabled() {
    static const bool val = (std::getenv("PROTO_ENV_DIAG") != nullptr);
    return val;
}

// NEW — initialized once at program startup; no per-call guard:
namespace {
    const bool g_diag_enabled = (std::getenv("PROTO_ENV_DIAG") != nullptr);
}
inline bool diagEnabled() { return g_diag_enabled; }
```

A namespace-scope `const bool` is a static storage duration variable initialized at program
startup (before `main()`). Accessing it requires only a single memory load from the data
segment — no guard, no TLS lookup, no branch. The compiler can also inline `diagEnabled()`
as a direct data-segment load and, in Release builds, may fold constant-propagation through
it if LTO is enabled.

The anonymous namespace prevents ODR violations when the header is included by multiple
translation units; each TU gets its own copy of `g_diag_enabled`, each initialized once
with the same `std::getenv` result.

### Remaining overhead analysis

After V99, the dominant costs in call_recursion are (from perf profiling of V98 — V99
should show similar distribution with guard-check lines reduced):

| Category                        | Estimated % | Nature               |
|---------------------------------|-------------|----------------------|
| `executeBytecodeRange` self     | ~24%        | interpreter loop     |
| `ProtoObject::getAttribute`     | ~6%         | object model         |
| `proto::isObject` type checks   | ~5%         | cross-DSO type tags  |
| `__tls_get_addr` TLS dispatch   | ~4%         | PLT/TLS overhead     |
| `hasPendingException` checks    | ~3%         | per-opcode safety    |
| `ProtoTuple::getSize`           | ~2%         | bytecode dispatch    |
| `_int_free`                     | ~0.5%       | (eliminated by V98)  |

The remaining 12.32× gap vs CPython is structural: protoPython and protoCore are separate
shared libraries, so every `getAttribute`, `isObject`, `getSize` call crosses the DSO
boundary (PLT stub + indirect branch + potential cache miss). CPython performs equivalent
operations as inline C struct field reads within a single binary.

Closing the gap further would require either:
1. Linking protoCore as a static library so LTO can inline across the boundary, or
2. Implementing a native C-level fast path for the hot bytecode dispatch loop that avoids
   cross-DSO calls for the most common operations (integer arithmetic, local variable load/store).
